## Project

Scaffolding for a **Power Pages** site written in plain HTML, CSS, and
JavaScript, deployed with the **pac CLI**. No build step, no dependencies.

**Power Pages is not static hosting.** There is no `index.html` served from a
folder. Site content lives in Dataverse as records — web pages, web templates
(Liquid), web files, content snippets, site settings — and this repository
holds the serialised form of those records, produced by `pac pages download`.

**There is no site content here yet.** This repository holds the conventions
and the deploy pipeline; the `site/` folder comes from a real Power Pages site.

## Stack

HTML5 · hand-written CSS · vanilla JavaScript · Liquid (Power Pages
templating) · no dependencies.

**HTML and CSS carry the site.** Every page must render, read, and navigate
with JavaScript disabled or still loading. JavaScript is for operations layered
on top — never for building the page, routing, or delivering the content a
visitor came for. There is no toolchain and no bundler.

**Never introduce** without recording the decision in this file:

- Frameworks (React, Vue, Svelte, Angular) and client-side routers
- Build tools, bundlers, `package.json`, `node_modules`, any lockfile
- CSS frameworks or preprocessors (Tailwind, Bootstrap, Sass, PostCSS)
- TypeScript — there is no compile step to strip types
- CDN `<script>` tags — Power Pages sites are often network-restricted

Allowed file types: `.html`, `.css`, `.js`, `.yml` (site records), `.liquid`,
`.md`, `.csv`, and images. Anything else needs a decision here.

## Commands

| Task | Command |
|---|---|
| install pac | `dotnet tool install --global Microsoft.PowerApps.CLI.Tool` |
| authenticate | `pac auth create --environment <environment-url>` |
| find the site | `pac pages list -v` (`-v` also shows the data model version) |
| download | `pac pages download --path site --webSiteId <id> --modelVersion <1\|2>` |
| upload | `pac pages upload --path site --modelVersion <1\|2>` |
| build / test / lint | none; TODO: Human clarification needed |

`pac` needs the .NET SDK; it is not a Node tool. There is no dev server and
**no full local preview** — Liquid, web roles, and Dataverse data only resolve
server-side, so verify by uploading to a development environment or in the
Power Pages design studio.

## Layout

Already present: `README.md`, this file, `.gitignore`, the deploy workflow, and
`specs/_template/spec.md` (copy it per feature to `specs/001-<feature>/spec.md`).

`site/` is **generated by `pac pages download` — never hand-author the tree.**
Create the site in Power Pages first, then download it. Its folders are record
types (`web-pages/`, `web-templates/`, `web-files/`, `page-templates/`,
`content-snippets/`, `site-settings/`, …), each with a `.yml` manifest beside
the content file. Follow the naming the download produces; do not invent it.

Where your code goes:

| Content | Lives in |
|---|---|
| Page body HTML | the web page's content-page HTML file under `web-pages/` |
| Layout and partials | `web-templates/` — Liquid is available here |
| CSS and JS assets | `web-files/`, served from the site root by partial URL |
| Data and config overrides | `deployment-profiles/<name>.deployment.yml` |

Two manifests sit at the site root: `manifest.yml` tracks deletions and **must
be committed**, or deletions never reach the target environment. The
environment manifest (`<org-url>-manifest.yml`) is per-developer state and is
git-ignored.

## Conventions

**Asset paths** — a web file is served from the site root at its partial URL,
so reference it as `/styles.css`. This is the opposite of a static-host subpath
rule. Confirm the partial URL on the record rather than assuming the filename.

**HTML** — semantic elements first (`<button>`, `<nav>`, `<main>`, `<label>`);
ARIA only where no native element fits. One `<h1>` per page, heading levels not
skipped. `alt` on every image, a `<label>` for every form control.

**CSS** — design tokens as custom properties on `:root`, declared once in the
shared stylesheet and named `--color-*`, `--space-*`, `--font-*`, `--radius`,
`--container`; rules reference tokens, never raw values. Define the light
palette on bare `:root`, override under `@media (prefers-color-scheme: dark)`.
Class names lowercase and hyphenated, one block per component; no
utility-class soup. No inline `style`, and no `!important` unless overriding a
browser default with no other hook — comment why. `box-sizing: border-box`
globally; Flexbox for one-dimensional layout, Grid for two-dimensional;
mobile-first with `min-width` queries; no fixed pixel page widths. Never remove
a focus ring without replacing it. Honour `prefers-reduced-motion`. Contrast at
least WCAG AA (4.5:1 body, 3:1 large). Token values are yours to pick —
TODO: Human clarification needed on brand palette, typefaces, and logo rules.

**JS** — optional and additive only. A page must be complete before its script
runs: no JS-rendered content, no client-side routing, no fetching the content a
visitor came to read. `const`/`let`, no globals, cache DOM queries, and prefer
a CSS or native-HTML solution (`<details>`, `<dialog>`, `:target`, a form) over
a script.

**Liquid** — presentation only. Keep logic minimal and never put a credential
or connection detail in a template.

**Language** — English for code, identifiers, file names, and documentation.

## Secrets and Access

Deployment uses a **service principal**. Credentials live in GitHub, never in
the repository:

| Name | Kind | Purpose |
|---|---|---|
| `PP_ENVIRONMENT_URL` | variable | target Dataverse environment URL |
| `PP_APP_ID` | variable | service principal application ID |
| `PP_TENANT_ID` | variable | tenant ID |
| `PP_MODEL_VERSION` | variable | `1` standard, `2` enhanced data model |
| `PP_CLIENT_SECRET` | **secret** | service principal client secret |

Anything in a web file or page HTML is downloadable by every visitor who can
reach that page, so no key belongs there. Who may read which page is governed
by web roles and table permissions — TODO: Human clarification needed on the

## Workflow

1. Copy `specs/_template/spec.md` to `specs/001-<feature>/spec.md` and fill in
   the acceptance criteria — they are both the prompt and the review checklist.
2. Implement two or three acceptance criteria at a time, not a whole spec.
3. Upload to a development environment and check against those criteria.
4. Branch off `main`, commit, open a pull request. Commit messages: English,
   imperative, one logical change each. Do not push to `main` directly.

Run `pac pages download` before *and* after deleting site content, so
`manifest.yml` records the deletion.

**Definition of Done**

- [ ] A spec exists and its acceptance criteria are met
- [ ] Verified in a Power Pages environment, with JavaScript disabled as well
- [ ] `manifest.yml` committed if anything was deleted
- [ ] Documentation updated in the same change
- [ ] No secrets committed

## Deployment

`.github/workflows/deploy-powerpages.yml` runs on push to `main`: checkout →
guard that `site/` exists → `actions-install` → `upload-paportal` with the
service principal. The action is still named `upload-paportal` even though the
CLI command is now `pac pages`.

Uploads within one environment are deltas driven by the manifests. A download
from environment A uploaded to environment B is always a **full** upload.
`--forceUploadAll` exists for drift, but is CLI-only and not exposed by the
action.

Rollback: revert the commit and push — the next run re-uploads the previous
state. Deletions only reverse if `manifest.yml` reflects them.

## Do / Don't

- **Do** read this file and the feature's `spec.md` first, write the spec before
  the code, and record each decision in the change that introduces it.
- **Do** get `site/` from `pac pages download`, and keep `manifest.yml`.
- **Don't** make a page depend on JavaScript to render, add anything from the
  exclusion list, or hand-author the `site/` tree.
- **Don't** commit a secret. Page HTML and web files are downloadable by any
  visitor who can reach the page — a key there is a published key.
